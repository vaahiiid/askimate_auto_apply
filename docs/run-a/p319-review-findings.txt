file: apps/conversation-service/src/run-driver.ts:7973

#putTheQuestion only says the atStart sentence when there is no assistant message after the demand's ordinal. That test was written for portal demands, which arrive in the middle of a run. A case-begin demand is appended by start() before any question, so any assistant message that comes before the funding question uses up that window. Concrete case: the student holds finance.funding {known:false} plus a full profile except one other field this entry requires (say identity.sex), and the entry is ASKS. start() appends value_part_demanded(finance.funding) at ordinal k. #decide then asks identity.sex first (value_asked at k+1, message at k+2). The student answers and confirms. When the walk reaches finance.funding, begun.ordinal is k and assistant messages exist after k, so demandSentence is skipped. The student sees "Please select your likely funding source\nEmployer\n…" with no word on why their earlier "no" is being reopened. The same happens when two fields get atStart demands (only the first field asked gets its sentence) and when a CV reading's sentence from #sayWhatArrived lands between the demand and the funding question. #sayWhatArrived skips atStart demands (line 11316), so nothing else says it. Test 2 only covers the case where funding is the very first question, because confirmTheInterview fills every other field.

driver 1  [medium]  The case-begin check runs outside the binding lock and depends on resumed=false, so a concurrent or retried start skips it and the run goes to a person
file: apps/conversation-service/src/run-driver.ts:3700

#askWhatTheFormAsksOfHeldAnswers runs after withBinding has committed startRun and released the lock, and only for the one caller that got resumed:false. (a) Race: two start() calls for one conversation, for example a client retrying a timed-out start, which the start() docstring names as expected. Caller 2 waits on the lock, finds the live run, gets resumed:true and goes straight to #decide. If that runs before caller 1 has appended the demand, the profile still shows finance.funding {known:false}. Under an absent:"ask" mapping, renderConfirmed returns no_such_part and planFill records render_refused on fundingSource and fundingStage. nextStep turns that structural blocker into a specialist step, and #stopForSpecialist raises an intervention, tells the student a person is looking, and saves the run as escalated. Caller 1 then appends the demand onto a run a person already holds. (b) Failure: if the profile load, wholeLog or append inside the check throws after startRun has committed, start() answers 500. Every retry then sees the live run, gets resumed:true and never runs the check, and advance() does not call it either, so the run ends at the same specialist stop. Whether the check has run should be read from the log (for example, an open or closed atStart demand), not from whether this caller created the run.

Verdict 1: stands.
I could not refute it. Both paths are reachable by reading the code as written. Defect: apps/conversation-service/src/run-driver.ts:3700 runs `if (!resumed) await this.#askWhatTheFormAsksOfHeldAnswers(...)` outside `withBinding`, after `startRun` has already committed a run with status "running" (packages/orchestrator/src/durable.ts:241-263). Whether the check has run is decided by a value held in memory (`resumed`), not by anything durable.

Concurrent path:
- A second `start()` blocks on the binding lock. Once it gets the lock, `findByCase` sees the live "running" run (`AUTOMATABLE_STATUSES` = running and suspended) and returns `resumed: true` (line 3535). It then goes straight to `#decide`.
- The worker can take the same path: `dueRuns` selects any running run, and `advance()` (around line 4110) never calls the check.
- If `#situation` reads `wholeLog` before caller 1 appends its demand, `demandsFrom` is empty. So `withoutDemanded` leaves the held `finance.funding {known:false}` in the profile view.

Failure path: if `profiles.load`, `wholeLog` or `append` inside the check throws, or the process dies, after `startRun` commits, `start()` throws. Every retry and every worker advance then gets `resumed: true` or goes through `advance()`, so the check never runs for that case.

Consequence once the prepared entry change is applied (fundingSource is a switch and fundingStage a part, both `absent: "ask"`):
1. format.ts `applyRule` returns `no_such_part`. P319's own format.test.ts asserts this.
2. In plan.ts:686-700, `chosenInstead` returns null for `no_such_part` (it handles only `no_matching_option` and `no_matching_case`), so planFill records `render_refused`.
3. `nextStep` (run.ts:551-562) treats any blocker other than `value_unavailable` as structural and returns `specialist`.
4. `#offerTheirChoice` cannot settle `no_such_part`. `#stopForSpecialist` (line 8633 on) raises an intervention, sends the 'blocked by the form' or specialist message, and saves status "escalated".

In the race, caller 1 then appends the demand and asks the funding question on a run that already has an open intervention. If caller 1's checkpoint lands first, the escalated save fails with `RunConcurrencyError`, which is swallowed. The intervention and the message stay anyway.

This breaks ADR-0161's stated behaviour that an answer given before the case "is asked for that part … when a case first plans". The ADR's "never on a resume" was meant to exclude existing cases, not a new case whose check never ran. It also breaks the file's own standard for a start retried after a crash, the case the `claimSubmissionKey` ordering comment designs for.

P319's tests do not cover this. The 'when a case begins' test uses a single start. The 'not on every resume' test advances the run and checks only that no demand was raised; it does not check that the run went to a person.
Verdict 2: stands.
I could not refute it. Every link in the scenario holds when I trace the code, and the failure case (b) does not depend on timing.

1. **The run is durable before the check runs.** `#openAndStart` (apps/conversation-service/src/run-driver.ts:3509-3684) calls `startRun` through `this.#options.stores`. That store uses the pool, not the binding's connection, so the run row with status "running" is committed on its own. `withBinding` (application-store.ts:210-270) then commits the binding. Only after that does run-driver.ts:3700 call `#askWhatTheFormAsksOfHeldAnswers`, and only when `resumed` is false. That check makes three database calls (`profiles.load`, `wholeLog`, `append`). None of them is caught, so an error in any of them propagates out of `start()`.

2. **No other path runs the check.**
   - A retried `start()` finds the live run at 3534-3535 and returns `resumed: true`, so 3700 skips the check.
   - `advance()` (4067) never calls it.
   - `dueForWorker` (work-store.ts:146-163) selects any "running" run whose conversation is bound. So the worker's next pass advances the new run even if the client never retries.
   - `demandsFrom` is the only thing that hides the field (run-driver.ts:4287-4293). It reads only the log, so with no `atStart` demand appended, the profile view still holds `finance.funding` as `{known:false}`.

3. **Without the demand, the run goes to a person.** Under the prepared patch's `absent:"ask"` mapping, `applyRule` returns `no_such_part` (format.ts diff). `planFill` turns that into a `render_refused` blocker (plan.ts:686-700). `chosenInstead` acts only on `no_matching_option` and `no_matching_case`, so it does not catch it. `nextStep` treats any blocker other than `value_unavailable` as structural and returns a specialist step (orchestrator run.ts:553-565). `#offerTheirChoice` declines `no_such_part` (entry-choice-offer.ts:129). `#stopForSpecialist` (8633-8722) then raises the intervention, tells the student a person is looking, and saves the run as "escalated". From then on the run stays with a person, because the check never runs again.

4. **The race in (a) is also plausible.** The second caller blocks on `SELECT … FOR UPDATE` until the first caller commits. It then sees the live run, gets `resumed: true`, and reads `wholeLog` in `#situation` (4277) a few round trips later. The first caller's `append` may not have committed by then. If so, the second caller escalates the run. The first caller then asks the funding question anyway, hits `RunConcurrencyError`, retries, and keeps "escalated". The student ends up with both "a person is looking" and the question.

**Why this counts as a defect here.** The codebase treats "a retry of a start that crashed between two steps" as a case it must handle at this very spot (the P38 comment at 3626-3631, and the route at routes.ts:1225-1229, which is idempotent on purpose). ADR-0161 says the held answer is checked "when the case first plans". In (b) the case's first plan happens without the check: the caller that created the run never reached `#decide`.

**What I checked against it.**
- The P319 test "is checked when a case begins and not on every resume" covers only a "no" written after the case had already planned. Nothing covers a check that failed or lost a race.
- The path is dormant on the entry as signed today, since nothing there says `ask`. It becomes reachable once the prepared change is signed, and that change is within the scope of this review.

Done: Fixed. The check runs in #openAndStart while the run has never been checkpointed (record.revision === 0), not on this call's `resumed`, so a start that failed before its first decide, or a second start that arrives before the first has decided, still checks; an open demand is not raised again, and two racing appends read as one. Moving the check inside the binding deadlocked (the binding holds the conversation's row, which an append waits on), so it stays after the lock. Tests (run-driver.test.ts, the P319 group): "is checked on a start that resumes a run never planned, as a start that failed before its first decide leaves it (P319's review)" and "is checked when a case begins and not on every resume: a no written after the case planned is not asked about". The racing second start is not driven by a test; it finds the same never-checkpointed run the first test builds. Mutations 10 and 11.

driver 2  [low]  An open case-begin demand outlives a change to the held answer made in another conversation: it says something false and re-asks a part already answered
file: apps/conversation-service/src/run-driver.ts:2219

demandsFrom closes a demand only on a value_confirmed in the same conversation's log. Conversation A starts on the ASKS entry with funding held as {known:false}, so A gets an atStart demand with partKey "source". Before A reaches funding, the student confirms finance.funding as {known:true, source:"employer", stage:"applying"} in another application's conversation B. In A the demand is still open: withoutDemanded hides the field, and seededWithDemands seeds from the confirmed entry (known=true, stage=applying) and deletes "source". The walk therefore asks the spec's own "Who is paying — self or family, employer, …" question. #putTheQuestion first says the atStart sentence: the form asks "Please select your likely funding source" and "What stage are you at with your funding?", "which your earlier answer … does not say. Let me ask you now." The held answer now answers both, the question that follows is not the form's, and the student is asked for a source they have already confirmed.

Verdict 1: refuted.
Refuted: the scenario can't happen in the system as it stands. By reading the code, the funding answer can't be changed in another conversation while conversation A's case-begin demand is open.

1. A confirmation in an application conversation is the only thing that writes the profile. `#persist` at run-driver.ts:8151 is the only `profiles.save` in apps/. `#interviewSituation` (run-driver.ts:7727) needs a bound case and run, so there is no conversation without a case that could ask.
2. finance.funding can't be changed by a typed correction. `refusedPart` (correction-requests.ts:233-236) returns "financial" for a closed part of a field in FINANCIAL_FIELDS. finance.funding is in that list (packages/profile/src/fields.ts:453-456), and known, source and stage are all closed. Conversation B could only write a new funding value through a walk opened by its own demand. That needs a second entry with `absent: "ask"` on funding, or a portal refusal on funding.
3. No second entry exists. docs/run-a/catalogue/entries holds only sheffield-pgt-2027-09.json, which has a single courseRef. The prepared patch only changes that one entry. `claimSubmissionKey` (run-driver.ts:3632-3651) refuses a second case for the same student, institution, course and intake. A reapplication needs the earlier case concluded, and a concluded case asks nothing more (run-driver.ts:7744 returns null for a completed run; a stopped application is refused by `#applicationStopFor`). So no A and B can be open at the same time for one student.
4. The part that lets a demand outlive a confirmation made elsewhere is not new in P319. `demandsFrom` closing only on a `value_confirmed` in the same conversation's log is P233's design; P319 only widened its type to carry `atStart`.
5. The finding contradicts itself on the sentence. "Before A reaches funding" means A asked other fields first. `#putTheQuestion` says the case-begin sentence only when no assistant message follows the demand (run-driver.ts:7973), so on that path the claimed false sentence is never said.

It would become a real defect once a second entry also asks the funding parts in the form's own words (or refuses funding) and two applications run side by side. That is a latent constraint waiting for that entry, not a scenario that can be reproduced on this diff.

Done: Refuted as worded (one verdict). Mended as a latent constraint (CLAUDE.md): #situation sets aside a case-begin demand once the held answer holds every part the form asks. Test: "a demand raised when the case began asks nothing once the held answer holds what the form asks, answered in another application (P319's review)". Mutation 12.

Verdict 1: stands.
The finding stands; tracing the new P319 code reproduces it. In packages/interview/src/interview.ts, readInFormWords (lines 410-431) works out `said = formWords(utterance)`. formWords (line 388-390) drops a closing full stop, so "Confirmed." becomes "confirmed". But `own = ownParse(utterance)` (line 414) runs the spec's own reader on the raw text, and that reader is oneOf(FUNDING_STAGE_WORDS) (field-specs.ts:775-778, 818-826, 960). oneOf only trims, lowercases and collapses spaces, so it looks up "confirmed." and returns null. The ruled-out check at line 415 then fails both ways. By value, "confirmed" is not null. By words, it compares against formWords("The funding has been confirmed"), which only matches the form's whole sentence. Nothing is near either: the four options offered are "I am applying for a project studentship", "I have applied for funding", "I am applying for funding" and "I am thinking about funding my studies this way", and none contains " confirmed ". So the student gets the generic reply at line 430, "I could not read one of the form's answers from \"Confirmed.\"", and never the ruledOut.because sentence. "My funding is confirmed" takes the same path. This breaks answer 6 in docs/run-a/p319-his-answers-on-the-thirteen-as-sent.txt ("If the student says their funding is confirmed, tell them that means the answer to \"Do you know…\" is yes"). It also breaks formWords' own promise that a closing full stop is set aside. The test at interview.test.ts:2208-2220 covers only "confirmed", "The funding has been confirmed" and "the funding has been CONFIRMED", so it cannot catch this. One correction to the finding: the explained refusal also spends an attempt, because attempts are counted at line 1101 before either path. So the real harm is that the student is never told how to get out of the question, not that an extra attempt is spent. They can keep refusing until the attempts run out and the run goes to a person.
Verdict 2: stands.
The finding holds. I confirmed it by reading the code and by running the same logic inline. At packages/interview/src/interview.ts:411-416 in the P319 diff, `readInFormWords` normalises the student's text with `formWords`, which lowercases, collapses spaces and strips a closing '.' or '!'. It then calls `own = ownParse(utterance)` on the raw text. `ownParse` is the stage part's `oneOf(FUNDING_STAGE_WORDS)` (packages/interview/src/field-specs.ts:778), which only trims, lowercases and collapses spaces, so it keeps the full stop. The ruled-out check passes in two cases: `formWords` of the form's sentence 'The funding has been confirmed' equals `said`, or `own === 'confirmed'`. For 'Confirmed.' the first test compares 'the funding has been confirmed' with 'confirmed' and fails. The second gets `own` = `oneOf('Confirmed.')`, which looks up 'confirmed.' and finds nothing (null), so it fails too. The near-match filter also finds nothing, because none of the four offered Sheffield options ('I am applying for a project studentship', 'I have applied for funding', 'I am applying for funding', 'I am thinking about funding my studies this way') contains ' confirmed '. The result is the generic reason 'I could not read one of the form's answers from "Confirmed."'. I reproduced this by running the same `formWords`, `oneOf` and filter logic inline with `node -e`, with no file written. 'confirmed' and 'The funding has been confirmed.' get the ruled-out explanation, while 'Confirmed.', 'confirmed!', 'My funding is confirmed' and 'It is confirmed' all get the generic refusal. So the same function treats a closing full stop differently depending on which path matches: the form's sentence with a full stop is told why, the single word with one is not. The cost is real. interview.ts:1101 spends an attempt before this path, a `not_understood` reply is returned, and after MAX_ATTEMPTS_PER_FIELD = 3 (interview.ts:229, 923-924) the field stops for a person. Meanwhile the student is never told what his answer 6 requires ('If the student says their funding is confirmed, tell them that means the answer to "Do you know…" is yes'). The test at packages/interview/src/interview.test.ts:2210 covers only 'confirmed', 'The funding has been confirmed' and 'the funding has been CONFIRMED', so this case is not tested. The free-phrasing half ('My funding is confirmed') is partly a design limit of exact, model-free reading. The 'Confirmed.' half is a plain normalisation defect: the fix is to read `ownParse` from the normalised text, or to strip the closing punctuation before calling it.

Done: Fixed. A ruled-out value is recognised by its sentence, by the part's own reading of the normalised text, or by its word said and not turned round (not, no, never, nothing, none, neither, nor, n't).
